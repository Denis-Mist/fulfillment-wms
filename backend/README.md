# Fulfillment WMS — бэкенд

ASP.NET Core (.NET 10 LTS) + PostgreSQL + EF Core. API повторяет контракт MSW-моков фронта (`frontend/src/mocks`),
чтобы фронт переключался с моков без переделок.

## Архитектура (Clean Architecture)

```
src/
  Wms.Domain          сущности и доменные правила, без внешних зависимостей
  Wms.Application     сценарии (handlers), интерфейсы портов, DTO, валидация  → Domain
  Wms.Infrastructure  EF Core/Npgsql, миграции, репозитории, JWT, хеширование, сид → Application
  Wms.Api             тонкие minimal-API эндпоинты, ProblemDetails, авторизация, CORS → Application, Infrastructure (только DI)
tests/
  Wms.Domain.Tests, Wms.Application.Tests       юнит-тесты
  Wms.Api.IntegrationTests                      WebApplicationFactory + Postgres (Testcontainers)
```

Зависимости направлены только внутрь; реализации подключаются через DI (`AddApplication`, `AddInfrastructure`).

## Запуск

Требуется .NET 10 SDK и Docker.

```bash
cd backend
docker compose up -d                 # PostgreSQL 17 на localhost:5432 (wms/wms)
dotnet run --project src/Wms.Api     # http://localhost:5080, миграции и сид применяются при старте
```

Фронт против бэкенда (в `frontend/.env.local`):

```
VITE_USE_MOCKS=false
VITE_API_BASE_URL=http://localhost:5080/api
```

CORS по умолчанию разрешён для `http://localhost:5173` (`Cors:Origins` в `appsettings.json`).

## Контракт

- База `/api`, JSON camelCase, enum — snake_case строки (`fc_owner`, `in_transit`).
- `Authorization: Bearer <JWT>`; организация выбирается заголовком `X-Organization-Id` (иначе первое членство;
  у `platform_admin` организации нет).
- Ошибки — RFC 7807 ProblemDetails `{ type, title, status, detail?, errors? }`.
- Списки — `Paged<T> { items, total, page, pageSize }`, параметры `page, pageSize, search, sortField, sortOrder`.
- Авторизация по ролям — политики `PlatformAdmin`, `Fulfillment`, `FulfillmentManagement`, `Worker`, `Seller`, `AnyMember`.

| Метод | Путь | Ответ |
|---|---|---|
| POST | /api/auth/login | 200 `{ accessToken, user }` / 401 |
| POST | /api/auth/register | 201 `{ accessToken, user }`, организация `pending` / 400 / 409 |
| GET | /api/auth/me | 200 `CurrentUser` / 401 |
| GET | /health | 200 |

Ключ подписи JWT в `appsettings.json` — только для разработки; в окружениях задавайте `Jwt__SigningKey`.

## Отклонения от моков (PR4: поставки, приёмка, размещение, задачи)

- Задачи (`tasks`) создаются при переходах статусов (arrive → задача приёмки, complete_receiving → задача размещения), а не генерируются при старте как в моке. В сид-снимке нет поставок в arrived/receiving/received, поэтому сидированных задач нет.
- Новая строка остатка при размещении создаётся в ячейке задачи размещения `STR[(idx·7) mod n]`, а не в случайной ячейке.
- Id задач — `tsk_{suffix}`; номер — `T-` + 6 последних цифр (100000 + seq·7), как в моке.
- Сид поставок — снимок мока на 2026-10-01 (статусы фиксированы, без пересчёта от текущей даты).
- Недостача/брак при приёмке — те же вероятности, что в моке (Mulberry32 от времени запроса), не детерминированы.
- Метрики заказов по-прежнему 0 (появятся с заказами); метрики поставок (`inbound30d`, активные поставки) заполнены.

## Отклонения от моков (PR5: остатки и журнал операций)

- `avgDailySales`/`daysOfCover` в `/stock/products` считаются из заказов за 30 дней; заказов в бэкенде пока нет, поэтому сейчас 0 и `null` (фильтр `lowStock=true` возвращает пусто). Подключится в PR заказов.
- Синтетический журнал (160 операций `op_seed_*`) — снимок `seedOperations()` на 2026-10-01 (Seeding/Data/operations.json), а не относительно текущей даты; сводка «за 30 дней» со временем перестанет их учитывать.
- Неизвестные значения фильтров `status` (остатки) и `type` (операции) игнорируются, а не дают пустой список, как в моке.
- Id пользовательской операции — `op_{base36 ms}_{suffix}` (в моке — случайные 4 символа), номер `OP-(20000 + число операций)` как в моке, но с учётом засеянных 160 (в моке тоже — `operations.all.length`).
- Некорректное или пустое тело POST → 404/422 по первой проверке (в моке — исключение при разборе JSON).

## Отклонения от моков (PR6a: заказы и продажи)
- Сид заказов экспортирован из моков на 2026-10-01Z; при сидировании все даты заказов сдвигаются на (текущее время − 2026-10-01), чтобы «последние 30 дней» и просрочки были актуальны. Поставки и операции не сдвигаются.
- Неизвестные значения `status`/`channel` игнорируются (фильтр не применяется), а не дают пустой список.
- `id` уведомления о просроченных заказах — `overdue_yyyy-MM-dd` (стабилен в течение дня), формат отличается от мока.
- Продажи (`avgDailySales`, `daysOfCover`, `lowStock` в остатках; `sold30d`/`orders30d`, тренды и статистика платформы) — по неотменённым заказам за 30 дней в области видимости пользователя.
- Поиск и уведомления по поставкам по-прежнему не реализованы.

## Отклонения от моков (PR6b: задания, комплектация, ТСД)
- Сид заданий (97 шт., `seedTasks()` на 2026-10-01Z) сдвигается по времени так же, как заказы.
- «Сегодня» (выработка, `doneToday`, список ТСД) — сутки UTC, в моке — локальное время браузера.
- Id батча — `tsk_b{suffix}` из генератора id (в моке — миллисекунды); номер `T-` как в моке (`100000 + n·7 + 3`).
- Базовый маршрут сортируется по коду ячейки ординально (в моке — `localeCompare`); для кодов вида `A-01-1` порядок совпадает.
- Порядок сотрудников в `/tasks/workers` — по id в естественном порядке (в моке — порядок массива пользователей).
- Неизвестные `status`/`type` в фильтрах заданий игнорируются; пустое тело `auto-assign` допустимо.
- Задание упаковки создаётся один раз на заказ (`tsk_p{orderId}`); повторное завершение не создаёт дубль.

### PR6c — персонал (/staff)

- `onShift` и `weekStart` считаются по московскому времени складов (Europe/Moscow), а не по локальному времени браузера, как в моке.
- `hiredAt` сидированных профилей сдвигается на ту же дельту, что и заказы (в моке — относительно `Date.now`).
- Профили существуют только для сидированных сотрудников (как в моке); новые участники организации в `/staff` не появляются, пока профиль не создан.
- Роль, выбранная в `PUT /staff/{id}`, хранится как `roleOverride` профиля и не меняет членство в организации (как в моке).
- Сортировка: по роли (порядковое сравнение кода роли), затем по ФИО (ru-RU).
- Отсутствующий/неизвестный `shift` в `POST /staff/{id}/shifts` → 422 «Некорректный день».

### PR6d — FBO-отгрузки (/fbo)

- Сидированные заявки (`fbo.json`, снимок seedFbo()) сдвигаются по времени, как заказы.
- `dueToday` — до конца текущих суток по московскому времени (в моке — локальное время браузера).
- Номер новой заявки — `FBO-{3100 + число заявок + 1}`, id — `fbo_u{suffix}`; `supplyId` при отправке — случайные 7 цифр с префиксом `WB-GI-`/`OZ-`, как в моке.

- Сортировка по умолчанию — `plannedAt` по убыванию (как listParams в моке).

### PR6e — возвраты (`/returns`): отклонения от моков

- Сидовые возвраты (`Seeding/Data/returns.json`, 64 шт.) сдвигаются во времени на `UtcNow − SnapshotAt`, как заказы.
- При закрытии годные позиции (`as_new`, `resale`) приходуются в первую по порядку сида ячейку остатка товара на складе возврата (`StockItem.Receive`); если остатка нет — ничего не приходуется, брак не создаёт записей карантина (как в моке).
- `inspect` без `grades` → 422 «Оцените все позиции» (в моке — исключение); пустой `comment` не сохраняется.
- `orderNumber`/`channel` берутся из заказа; если заказа нет — `"—"` и `wb`.
- Неизвестные значения фильтров `status`/`reason` игнорируются; сортировка по умолчанию — `createdAt desc`.
- `restockRate` округляется до целого процента (AwayFromZero).

### PR7 — биллинг и интеграции: отклонения от моков

- Начисления (`/billing/charges`, `/billing/summary`) считаются детерминированно из реальных заказов/приёмок и синтетического суточного потока, но ГПСЧ (mulberry32) засевается хешем ключа (договор/день/заказ), поэтому суммы не совпадают с моком побайтно.
- Тарифы и акты хранятся в PostgreSQL (`tariffs`, `billing_acts`), а не в localStorage; создаются лениво при первом обращении: тариф по умолчанию по формуле мока, акты за 3 прошлых месяца (выставлены 3-го числа следующего месяца, старше одного месяца — оплачены через 6 дней). Черновик текущего месяца — виртуальный `draft_{contractId}`.
- Месяцы/дни считаются в UTC (мок — локальное время браузера).
- Интеграции хранятся в `marketplace_integrations` (журнал — jsonb, ≤30 записей); демо-состояние сидируется при первом GET организации. Параллельный первый запрос не даёт 500 на уникальном ключе `(organization_id, channel)`: повторная вставка перечитывает уже сохранённые строки. Ключ API после `POST /integrations/{channel}/connect` сохраняется в `api_key_cipher` (AES-GCM) и в ответах не возвращается — только `keyMask`. Сидовые подключения ключа не содержат: `POST /integrations/wb/sync` без повторного connect даёт 422 «Ключ API не сохранён». `connect` не проверяет ключ у маркетплейса — в журнале «Кабинет подключён».
- WB и Ozon: `sync` ходит в HTTP API. Для WB в Development по умолчанию sandbox; у Ozon официального sandbox URL нет — используется `https://api-seller.ozon.ru` в режиме чтения.
- В ответ интеграций добавлены поля `environment` (`sandbox` | `production`), `lastError`, `lastHttpStatus`. После ошибки API статус становится `error` (раньше бэкенд отдавал только `connected` / `disconnected`). Неизвестный канал → 404, неизвестные значения фильтров (`service`) игнорируются.

### PR8 — дашборды и аналитика: отклонения от моков
- Границы дней/периодов считаются в UTC (мок — локальное время браузера); даты в ответах — ISO с `Z`.
- Утверждённый план персонала (`/analytics/forecast/approve`) и применённые перемещения слоттинга (`/analytics/slotting/apply`) хранятся в PostgreSQL (`staff_plans`, `slotting_applied`), а не в localStorage.
- Синтетический ряд KPI больше не строится — см. FR-17. Прогноз нагрузки (`/analytics/forecast`) берётся из реальных заказов — см. FR-16. Слоттинг считается по остаткам, габаритам и оборачиваемости — см. FR-12. Значения могут отличаться от моков.
- `period` KPI ограничивается 1–56, `horizon` прогноза — 7–28 (значение вне диапазона сжимается; в GET `horizon=50` → 28); неизвестный `algorithm` в GET и в approve → 422 «Неизвестный алгоритм»; если параметр не передан — значение по умолчанию (`holt_winters` / `abc_affinity`).
- `slotting/apply` с пустым списком `ids` → 422; неизвестные id не применяются и не пишутся в `slotting_applied`, `applied` считает только успешные перемещения.
- Дашборд ФЦ для селлера и наоборот → 403; аналитика доступна только fc_owner/fc_manager.
- Расхождения по поставкам — по доменному `HasDiscrepancy`.

### FR-16 — прогноз нагрузки из реальных заказов

- История для `GET /analytics/forecast` строится из PostgreSQL, а не из синтетического ряда по сиду:
  неотменённые заказы (`status != cancelled`) по `CreatedAt` в сутках UTC за 56 дней до сегодняшнего; сегодняшний день в историю не входит.
- Строки отбора (`tasks` типа `picking`, не отменённые) входят в ту же суточную корзину как `PickLines` и подстраховывают среднее число единиц на заказ, если у заказов нет количеств.
- Среднее единиц на заказ считается по строкам заказов; иначе — по строкам отбора; иначе норматив мока `2.6`. От него считается `staffing.units` и потребность в персонале.
- Алгоритмы переключаются query-параметром `algorithm` (как на фронте):
  - `holt_winters` (по умолчанию) — аддитивный Хольт–Уинтерс с недельным сезоном (α=0.35, β=0.05, γ=0.3);
  - `moving_average` — базовый прогноз, среднее за последние 7 дней.
- Backtest за 14 дней: MAPE и MAE выбранного алгоритма; `baselineMape` — ошибка скользящего среднего на том же окне.
- `POST /analytics/forecast/approve` без изменений: план персонала пишется в `staff_plans` (алгоритм по умолчанию `holt_winters`, неизвестный — 422).
- Контракт ответа совместим с фронтом. В `meta.version` для прогноза — `2.0.0`; `meta.dataVersion` имеет вид `orders-{n}-picks-{n}-snap-yyyy-MM-dd`; `meta.seed` по-прежнему хеш складов (идентификация среза, а не генератор истории).
- Дни считаются в UTC, как и остальная аналитика бэкенда.

### FR-12 — слоттинг с габаритами, массой и вместимостью

- `GET /analytics/slotting` считает ABC по реальным строкам неотменённых заказов за 30 дней (без синтетического множителя и шума). SKU, давшие до 80% отборов, — класс A (включая доминирующий товар).
- Рекомендация перемещения строится только для класса A вдали от входа (дистанция > 12 м) в более близкую ячейку (выигрыш ≥ 4 м).
- Ячейка должна вместить объём остатка (`product.volumeLiters × quantity ≤ capacityLiters − занято`). Разные SKU в одну ячейку не смешиваются. Тяжёлые товары (≥ 1000 г) предпочтительно ставятся на нижние ярусы.
- Алгоритмы: `abc` — базовый ABC; `abc_affinity` (по умолчанию) — плюс сродство SKU, которые часто отбираются вместе. Переключение: `?algorithm=abc` или `abc_affinity`.
- `gain` — оценка сокращения пробега за 30 дней (м): отборы × (from − to) × 2, с надбавкой 12% при affinity.
- `POST /analytics/slotting/apply` переносит только свободный остаток (`Take`/`Receive`), резерв остаётся в исходной ячейке; вместимость проверяется повторно. Инварианты: сумма quantity и reserved не меняется, отрицательного остатка нет. Несуществующие id не попадают в `slotting_applied` и не увеличивают `applied`.
- Контракт совместим с фронтом. Аддитивные поля хода: `volumeLiters`, `weightG`, `capacityLiters`. `meta.version` слоттинга — `2.0.0`.

### FR-13 / FR-14 — автоформирование партий и маршруты

- `GET /picking/suggestions?warehouseId=` считает партии без записи в БД: жадная волна от самого срочного заказа, ограничение тары 60 л, не больше 12 заказов, штраф за отгрузку дальше 2 часов от начала волны, минимизация прироста длины оптимизированного маршрута.
- `POST /picking/batches/auto` с `{ warehouseId, algorithm }` (и `POST /picking/batches` с `auto: true`) создаёт все предложенные партии склада. Пустое тело и `{ orderIds: [] }` без `auto` по-прежнему дают 422 «Выберите заказы».
- Ручное `POST /picking/batches` с явным списком заказов не изменилось (лимит 12, один склад).
- Для каждой созданной партии сохраняются `optimizedDistance`, `baselineDistance`, `estimatedMinutes` (по выбранному алгоритму), `volumeLiters`, `toteCapacityLiters`. В `TaskDetails` те же поля плюс `toteFill` (доля заполнения тары). Старые задания без метрик считаются при чтении, как раньше.
- Маршрут: `algorithm=optimized` (ближайший сосед + 2-opt, по умолчанию) или `baseline` (сортировка по коду ячейки). Длина оптимизированного маршрута не больше базового; порядок шагов совпадает с выбранным алгоритмом.
- Оценка времени: `(длина_м / 1.2 + единицы×6 + шаги×10) / 60` минут, минимум 1.

### FR-15 — назначение с учётом смены и квалификации

- `POST /tasks/auto-assign` по-прежнему берёт новые задания сначала срочные, затем более старые и не даёт сотруднику больше трёх активных.
- Сотрудник с кадровым профилем назначается, только если сейчас на смене (`staff` график, местное время склада Europe/Moscow, как в модуле персонала). Без профиля доступность как раньше — только роль и загрузка.
- Из подходящих по роли предпочтителен сотрудник с навыком под тип задания (приёмка/размещение — receiving, отбор — picking, упаковка — packing, инвентаризация — inventory, перемещение — picking, receiving или forklift). Если таких нет, берётся любой с нужной ролью.
- Среди квалифицированных предпочтителен сотрудник своего склада, затем менее загруженный, бригадир — в последнюю очередь.
- Ручное `POST /tasks/{id}/assign` по-прежнему проверяет только роль (смену и навык можно обойти сознательно). Несуществующий `userId` → 404 «Сотрудник не найден»; неподходящая роль → 422.
- В `GET /tasks/workers` аддитивные поля: `onShift`, `available`, `warehouseId`, `skills`.

### FR-17 — KPI по реальным данным

- `GET /analytics/kpi` больше не использует синтетический ряд: сутки в UTC, как у прогноза (окно `[сегодня − period, сегодня)`, сегодняшний день не входит).
- `orders` — неотменённые заказы по `CreatedAt`. `processingHours` — среднее время от создания до отгрузки (`ShippedAt`) за сутки отгрузки; если отгрузок нет, берётся длительность завершённых заданий.
- `routeBaseline` / `routeOptimized` — средняя длина маршрута заданий отбора за сутки (сохранённые метрики партии или пересчёт baseline vs optimized по ячейкам). `routeReductionPct` — сравнение «до/после» алгоритма маршрутизации по тем же заданиям.
- `errors` — списания и операции с причиной расхождения; `utilization` — минуты работы завершённых заданий относительно графика персонала (12 ч на вышедшего сотрудника).
- Разрезы `bySeller` (клиент) и аддитивный `byWarehouse` (склад): заказы, среднее время обработки и доля ошибок.

### Исправления QA, FR-модули (BE-FR-1…BE-FR-4)

- **BE-FR-1 / BE-FR-2**: неизвестный `algorithm` в `GET /analytics/forecast` и `GET /analytics/slotting` → 422 «Неизвестный алгоритм» (как в `POST /analytics/forecast/approve`). Если параметр не передан, используются значения по умолчанию: `holt_winters` и `abc_affinity`.
- **BE-FR-3**: `POST /analytics/slotting/apply` записывает в `slotting_applied` и считает в `applied` только реально выполненные перемещения. Неизвестные id игнорируются (`applied: 0` для `["slot_does_not_exist"]`).
- **BE-FR-4**: `POST /tasks/{id}/assign` с несуществующим `userId` → 404 «Сотрудник не найден». Неподходящая роль по-прежнему даёт 422.


### Интеграции: Wildberries sandbox

Тестовый токен выпускается в личном кабинете продавца WB: в настройках API выберите scope **Test**. Он работает только с sandbox-хостами и не трогает реальный магазин. Документация: https://dev.wildberries.ru/sandbox и https://dev.wildberries.ru/docs/openapi/api-information.

Переменные окружения:

- `WB_TEST_TOKEN` — для ручного smoke-теста `WbSandboxSmokeTests` (без переменной тест сразу выходит и не падает в CI).
- `Marketplace:ProtectionKey` (иначе `Jwt:SigningKey`) — ключ шифрования `api_key_cipher`.
- `Marketplace:AllowProductionStockPush` — разрешить выгрузку остатков на боевые хосты (по умолчанию `false`). В sandbox выгрузка идёт, если у подключения включён `pushStock`.
- `Marketplace:DefaultEnvironment` — если не задано: `sandbox` в Development, `production` в остальных средах. Можно передать `environment` в теле `connect` / `PUT /integrations/{channel}`.

Что дергает WMS при `POST /api/integrations/wb/sync` (после `connect`):

| Шаг | Хост (sandbox) | Метод |
|---|---|---|
| Проверка токена | `marketplace-api-sandbox.wildberries.ru/ping` | GET |
| Новые заказы FBS | `.../api/v3/orders/new` (если пусто — `.../api/v3/orders` за 7 дней, страницы по `next`, до 10×1000) | GET |
| Карточки | `content-api-sandbox.wildberries.ru/content/v2/get/cards/list` | POST |
| Склады и остатки | `.../api/v3/warehouses`, `PUT .../api/v3/stocks/{id}` пачками по 1000 SKU | GET / PUT |
| Тестовый заказ | `POST .../api/v3/test/fbs/orders/make` | метод клиента есть, обычный sync его не вызывает |

Боевые хосты — те же пути на `marketplace-api.wildberries.ru` и `content-api.wildberries.ru`. Заголовок `Authorization` — сам токен, как в документации WB. Ошибки API возвращаются как ProblemDetails 422 (ответ 4xx) или 502 (сеть / 5xx) с текстом маркетплейса в `detail`; то же пишется в `lastError` / журнал.

`connect` ключ только сохраняет и не пингует маркетплейс. Журнал при этом пишет «Кабинет подключён», без претензии, что ключ уже проверен. Секреты в git не коммитятся.

Число в строке «Заказов FBS в кабинете» — это количество отправлений в кабинете, а не заказы, созданные в WMS. Повторные SKU в выгрузке складываются. Пустой каталог не вызывает API складов. Если `pushStock` включён, но запись в боевой контур запрещена (`AllowProductionStockPush=false`, а для WB ещё и среда не sandbox), синхронизация всё равно успешна, а в журнале появляется «Остатки не выгружены: запись в боевой кабинет отключена». Обрыв HTTP-запроса клиента не записывается как ошибка маркетплейса.

### Интеграции: Ozon Seller API

Ключи создаются в кабинете продавца: [seller.ozon.ru](https://seller.ozon.ru) → Настройки → Seller API (`Client-Id` и `Api-Key`). Официальная документация: https://docs.ozon.ru/api/seller/. Отдельного sandbox-хоста в этих документах нет, поэтому WMS ходит на боевой `https://api-seller.ozon.ru`. В режиме `sandbox` (и по умолчанию без флага) обновление остатков **не выполняется** — только чтение. Выгрузка остатков на этот хост возможна, только если явно включить `Marketplace:AllowProductionStockPush` и `pushStock` у подключения.

Переменные окружения для ручного smoke-теста `OzonSellerSmokeTests` (без них тест сразу выходит):

- `OZON_CLIENT_ID`
- `OZON_API_KEY`

Что дергает WMS при `POST /api/integrations/ozon/sync` (после `connect` с `apiKey` и `clientId`):

| Шаг | Путь на `api-seller.ozon.ru` | Метод |
|---|---|---|
| Проверка ключей | `/v1/roles` | POST |
| Товары | `/v3/product/list` | POST |
| Отправления FBS | `/v4/posting/fbs/list` (за 7 дней, страницы по 100, пока `has_next`, не больше 20) | POST |
| Отправления FBO | `/v2/posting/fbo/list` (за 7 дней, первая страница; в счётчик FBS не входит) | POST |
| Остатки | `/v1/warehouse/list` (берётся активный склад), затем `/v2/products/stocks` пачками по 100 | POST, только если разрешена запись |

Заголовки: `Client-Id` и `Api-Key`. Ошибки — те же 422/502 ProblemDetails с текстом Ozon в `detail`. Ответ 200, в котором у позиции `updated: false` или непустой `errors`, тоже становится 422: в тексте есть число принятых SKU и первая ошибка Ozon. Для выгрузки выбирается склад со статусом `created` или `new`, а не первый попавшийся отключённый.

### Поля интеграций для фронтенда

Контракт `GET /api/integrations`, `POST /integrations/{channel}/connect|sync|disconnect` и `PUT /integrations/{channel}` остаётся совместимым: прежние поля (`channel`, `status`, `keyMask`, `clientId`, `connectedAt`, `lastSyncAt`, `autoImportFbs`, `pushStock`, `syncIntervalMin`, `log`) не менялись. Добавлены только новые:

| Поле | Тип | Когда появляется |
|---|---|---|
| `environment` | `"sandbox"` \| `"production"` | Всегда. Для WB в Development по умолчанию `sandbox`. Можно передать в теле `connect` или `PUT` (`environment`). |
| `lastError` | `string` | После неудачного `sync`; при успехе поле отсутствует (`null` не сериализуется). |
| `lastHttpStatus` | `number` | HTTP-статус ответа маркетплейса (например 401 или 200) или отсутствует. |
| `status` | дополнительно `"error"` | После ошибки API. Кабинет остаётся подключённым (ключ сохранён), повторный `sync` допустим. |

`api_key` / сам ключ в ответах никогда не возвращается — только `keyMask` (`••••` + 4 последних символа). Для `connect` на Ozon по-прежнему нужны `apiKey` и `clientId`.
