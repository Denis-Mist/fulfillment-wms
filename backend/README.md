# Fulfillment WMS — бэкенд

ASP.NET Core (.NET 10 LTS) + PostgreSQL + EF Core. API повторяет контракт MSW-моков фронта (`frontend/src/mocks`),
чтобы фронт переключался с моков без переделок.

## Архитектура (Clean Architecture)

```
src/
  Wms.Domain          сущности и доменные правила, без внешних зависимостей
  Wms.Application     сценарии (handlers), интерфейсы портов, DTO, валидация  → Domain
  Wms.Infrastructure  EF Core/Npgsql, миграции, репозитории, JWT, хеширование, сид → Application
  Wms.Api             тонкие minimal-API эндпоинты, ProblemDetails, авторизация, CORS → Application, Infrastructure (только DI)
tests/
  Wms.Domain.Tests, Wms.Application.Tests       юнит-тесты
  Wms.Api.IntegrationTests                      WebApplicationFactory + Postgres (Testcontainers)
```

Зависимости направлены только внутрь; реализации подключаются через DI (`AddApplication`, `AddInfrastructure`).

## Запуск

Требуется .NET 10 SDK и Docker.

```bash
cd backend
docker compose up -d                 # PostgreSQL 17 на localhost:5432 (wms/wms)
dotnet run --project src/Wms.Api     # http://localhost:5080, миграции и сид применяются при старте
```

Фронт против бэкенда (в `frontend/.env.local`):

```
VITE_USE_MOCKS=false
VITE_API_BASE_URL=http://localhost:5080/api
```

CORS по умолчанию разрешён для `http://localhost:5173` (`Cors:Origins` в `appsettings.json`).

## Контракт

- База `/api`, JSON camelCase, enum — snake_case строки (`fc_owner`, `in_transit`).
- `Authorization: Bearer <JWT>`; организация выбирается заголовком `X-Organization-Id` (иначе первое членство;
  у `platform_admin` организации нет).
- Ошибки — RFC 7807 ProblemDetails `{ type, title, status, detail?, errors? }`.
- Списки — `Paged<T> { items, total, page, pageSize }`, параметры `page, pageSize, search, sortField, sortOrder`.
- Авторизация по ролям — политики `PlatformAdmin`, `Fulfillment`, `FulfillmentManagement`, `Worker`, `Seller`, `AnyMember`.

| Метод | Путь | Ответ |
|---|---|---|
| POST | /api/auth/login | 200 `{ accessToken, user }` / 401 |
| POST | /api/auth/register | 201 `{ accessToken, user }`, организация `pending` / 400 / 409 |
| GET | /api/auth/me | 200 `CurrentUser` / 401 |
| GET | /health | 200 |

Ключ подписи JWT в `appsettings.json` — только для разработки; в окружениях задавайте `Jwt__SigningKey`.

## Отклонения от моков (PR2: организации, справочники, настройки)

- Метрики складов/заказов/остатков в карточках и обзоре пока нулевые (`NullOperationalMetrics`) — появятся в PR3+.
- Аудит, уведомления и поиск наполняются только из реализованных доменов (организации, справочники, пользователи); остальные источники — в следующих PR.
- `reset-password` реально меняет хэш пароля (мок только возвращает временный пароль).
- При одобрении организации без настроек создаются настройки по умолчанию (мок отдаёт 404).
- Неизвестное значение enum-фильтра в списках игнорируется (как в моке, без 400).
- Заявки клиентов сидируются относительно момента сида; базовая дата сида — 2026-10-01.
- Даты сериализуются в UTC с суффиксом `Z` (как в моке).
- Заблокированные пользователи могут входить — как в моке.

## Отклонения от моков (PR3: склады, зоны, ячейки, каталог)

- `POST /api/warehouses/{id}/zones` с неизвестным `type` → 400 «Неизвестный тип зоны» (мок принимает любое значение).
- Фильтр `occupancy` ячеек повторяет мок: `empty`, `full`, любое другое непустое значение — «частично заполненные».
- `sold30d`/`orders30d` с PR6a считаются по реальным заказам; входящие объёмы пока 0; `productsCount`, остатки и резервы — реальные (резервы из сида).
- Идентификаторы новых товаров — `prd_{suffix}`.

## Отклонения от моков (PR4: поставки, приёмка, размещение, задачи)

- Задачи (`tasks`) создаются при переходах статусов (arrive → задача приёмки, complete_receiving → задача размещения), а не генерируются при старте как в моке. В сид-снимке нет поставок в arrived/receiving/received, поэтому сидированных задач нет.
- Новая строка остатка при размещении создаётся в ячейке задачи размещения `STR[(idx·7) mod n]`, а не в случайной ячейке.
- Id задач — `tsk_{suffix}`; номер — `T-` + 6 последних цифр (100000 + seq·7), как в моке.
- Сид поставок — снимок мока на 2026-10-01 (статусы фиксированы, без пересчёта от текущей даты).
- Недостача/брак при приёмке — те же вероятности, что в моке (Mulberry32 от времени запроса), не детерминированы.
- Метрики заказов по-прежнему 0 (появятся с заказами); метрики поставок (`inbound30d`, активные поставки) заполнены.

## Отклонения от моков (PR5: остатки и журнал операций)

- `avgDailySales`/`daysOfCover` в `/stock/products` считаются из заказов за 30 дней; заказов в бэкенде пока нет, поэтому сейчас 0 и `null` (фильтр `lowStock=true` возвращает пусто). Подключится в PR заказов.
- Синтетический журнал (160 операций `op_seed_*`) — снимок `seedOperations()` на 2026-10-01 (Seeding/Data/operations.json), а не относительно текущей даты; сводка «за 30 дней» со временем перестанет их учитывать.
- Неизвестные значения фильтров `status` (остатки) и `type` (операции) игнорируются, а не дают пустой список, как в моке.
- Id пользовательской операции — `op_{base36 ms}_{suffix}` (в моке — случайные 4 символа), номер `OP-(20000 + число операций)` как в моке, но с учётом засеянных 160 (в моке тоже — `operations.all.length`).
- Некорректное или пустое тело POST → 404/422 по первой проверке (в моке — исключение при разборе JSON).

## Отклонения от моков (PR6a: заказы и продажи)
- Сид заказов экспортирован из моков на 2026-10-01Z; при сидировании все даты заказов сдвигаются на (текущее время − 2026-10-01), чтобы «последние 30 дней» и просрочки были актуальны. Поставки и операции не сдвигаются.
- Неизвестные значения `status`/`channel` игнорируются (фильтр не применяется), а не дают пустой список.
- `id` уведомления о просроченных заказах — `overdue_yyyy-MM-dd` (стабилен в течение дня), формат отличается от мока.
- Продажи (`avgDailySales`, `daysOfCover`, `lowStock` в остатках; `sold30d`/`orders30d`, тренды и статистика платформы) — по неотменённым заказам за 30 дней в области видимости пользователя.
- Поиск и уведомления по поставкам по-прежнему не реализованы.

## Отклонения от моков (PR6b: задания, комплектация, ТСД)
- Сид заданий (97 шт., `seedTasks()` на 2026-10-01Z) сдвигается по времени так же, как заказы.
- «Сегодня» (выработка, `doneToday`, список ТСД) — сутки UTC, в моке — локальное время браузера.
- Id батча — `tsk_b{suffix}` из генератора id (в моке — миллисекунды); номер `T-` как в моке (`100000 + n·7 + 3`).
- Базовый маршрут сортируется по коду ячейки ординально (в моке — `localeCompare`); для кодов вида `A-01-1` порядок совпадает.
- Порядок сотрудников в `/tasks/workers` — по id в естественном порядке (в моке — порядок массива пользователей).
- Неизвестные `status`/`type` в фильтрах заданий игнорируются; пустое тело `auto-assign` допустимо.
- Задание упаковки создаётся один раз на заказ (`tsk_p{orderId}`); повторное завершение не создаёт дубль.

### PR6c — персонал (/staff)

- `onShift` и `weekStart` считаются по московскому времени складов (Europe/Moscow), а не по локальному времени браузера, как в моке.
- `hiredAt` сидированных профилей сдвигается на ту же дельту, что и заказы (в моке — относительно `Date.now`).
- Профили существуют только для сидированных сотрудников (как в моке); новые участники организации в `/staff` не появляются, пока профиль не создан.
- Роль, выбранная в `PUT /staff/{id}`, хранится как `roleOverride` профиля и не меняет членство в организации (как в моке).
- Сортировка: по роли (порядковое сравнение кода роли), затем по ФИО (ru-RU).
- Отсутствующий/неизвестный `shift` в `POST /staff/{id}/shifts` → 422 «Некорректный день».

### PR6d — FBO-отгрузки (/fbo)

- Сидированные заявки (`fbo.json`, снимок seedFbo()) сдвигаются по времени, как заказы.
- `dueToday` — до конца текущих суток по московскому времени (в моке — локальное время браузера).
- Номер новой заявки — `FBO-{3100 + число заявок + 1}`, id — `fbo_u{suffix}`; `supplyId` при отправке — случайные 7 цифр с префиксом `WB-GI-`/`OZ-`, как в моке.
- Неизвестные `status`/`marketplace` в фильтрах игнорируются; отсутствующий `to` в `advance` → 409 «Недопустимый переход статуса».
- Сортировка по умолчанию — `plannedAt` по убыванию (как listParams в моке).

### PR6e — возвраты (`/returns`): отклонения от моков

- Сидовые возвраты (`Seeding/Data/returns.json`, 64 шт.) сдвигаются во времени на `UtcNow − SnapshotAt`, как заказы.
- При закрытии годные позиции (`as_new`, `resale`) приходуются в первую по порядку сида ячейку остатка товара на складе возврата (`StockItem.Receive`); если остатка нет — ничего не приходуется, брак не создаёт записей карантина (как в моке).
- `inspect` без `grades` → 422 «Оцените все позиции» (в моке — исключение); пустой `comment` не сохраняется.
- `orderNumber`/`channel` берутся из заказа; если заказа нет — `"—"` и `wb`.
- Неизвестные значения фильтров `status`/`reason` игнорируются; сортировка по умолчанию — `createdAt desc`.
- `restockRate` округляется до целого процента (AwayFromZero).

### PR7 — биллинг и интеграции: отклонения от моков

- Начисления (`/billing/charges`, `/billing/summary`) считаются детерминированно из реальных заказов/приёмок и синтетического суточного потока, но ГПСЧ (mulberry32) засевается хешем ключа (договор/день/заказ), поэтому суммы не совпадают с моком побайтно.
- Тарифы и акты хранятся в PostgreSQL (`tariffs`, `billing_acts`), а не в localStorage; создаются лениво при первом обращении: тариф по умолчанию по формуле мока, акты за 3 прошлых месяца (выставлены 3-го числа следующего месяца, старше одного месяца — оплачены через 6 дней). Черновик текущего месяца — виртуальный `draft_{contractId}`.
- Месяцы/дни считаются в UTC (мок — локальное время браузера).
- Интеграции WB/Ozon хранятся в `marketplace_integrations` (журнал — jsonb, ≤30 записей); демо-состояние сидируется при первом GET организации. Обмен с маркетплейсами имитируется (`sync` даёт случайные 0–6 заказов и 60–159 SKU), ключ API не сохраняется — только маска.
- Неизвестный канал → 404, неизвестные значения фильтров (`service`) игнорируются.
